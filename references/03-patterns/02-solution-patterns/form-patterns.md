## 1. 定位与适用范围

本方法用于在业务模型、字段清单、字段属性、默认值、依赖关系、风险操作、业务约束和交互契约基本明确后，设计通用表单与配置页面。它不重新判断业务模块归属，不覆盖上游已经确定的保存、取消、返回、确认、权限和生命周期规则。

设计表单时先区分两层规则：

- 通用方法层：结合页面模板确定表单承载方式，并设计信息分层、组件选择原则、风险交互、默认值、校验、状态和输出契约，适用于多数 B 端表单设计。
- 产品实现层：决定具体组件库、视觉样式、间距、项目内样例和页面参考。若项目已经指定 idux，则优先使用 idux 组件；若无对应组件，不得私自替代，应输出组件缺口说明，并给出“现有组件组合方案”和“新增组件需求”两种建议，标明是否需要设计系统评审。

当通用方法与业务专属规则、用户明确要求或产品实现层规范冲突时，优先级为：用户明确要求 > 业务场景约定规则 > 产品实现层规范 > 通用方法。新场景与既有规则冲突时，应保留原规则、显式标注冲突、提出建议修订，并交由负责人确认。

## 2. 待确认策略

不要因为存在少量不确定信息就阻塞整体方案输出。按影响程度区分前置确认与后置确认：

- 前置确认：会影响表单承载方式、核心流程、保存逻辑、权限边界、关键业务规则或数据状态闭环的问题，必须先确认再继续。
- 后置确认：不影响主体方案成立，只影响局部字段文案、默认值、排序、次要校验或低风险配置的问题，可先基于默认假设输出方案，并在方案后集中列出。
- 默认假设：信息缺失但可按常见 B 端设计实践推进时，先明确写出默认假设，再继续输出方案。

调整步骤、表单承载方式、表单分组或表单上下文时，必须说明受影响的上游交互契约，并加入 `regression_scope`，避免因视觉结构变化削弱既有行为。

## 3. 常见字段组件映射速查

收到字段清单后，先匹配下表中的高频字段类型；命中时优先按推荐组件设计，未命中时再进入后续承载方式、分层布局与字段设计规则。

| 常见字段 | 推荐组件 | 适用说明 | 设计要点 |
| --- | --- | --- | --- |
| 名称 / 描述 | `IxInput` | 用于输入名称、描述、备注等常规信息 | 名称通常使用单行输入；描述较长时可按内容长度升级为多行输入。 |
| IP / 域名 | `IxProTextarea` | 需要输入多个 IP、域名或同类地址对象，且有特定格式要求 | 一行一个对象展示，支持逐行校验和错误定位，避免用户用逗号、空格混输。 |
| 状态 / 动作 | `IxRadio` / `IxRadioGroup` | 例如启用 / 禁用、允许 / 拒绝、允许 / 阻断等互斥状态或动作 | 一组选项必须通过 `IxRadioGroup` 管理；需要按钮样式时使用 `buttoned`，不要用按钮或标签模拟单选。 |
| XX 地址 | `IxInput` | 输入对象有明确前缀或后缀，需要减少用户输入错误 | 通过 `addonBefore` 与 `addonAfter` 在输入框前后添加固定标签或控件，例如协议前缀 `https://`、域名后缀 `.com`。 |
| 密码 | `IxInput` | 需要用户输入密码、密钥或敏感口令 | 通过输入框组件能力和前后缀插槽承载图标、可见性切换等内容；不要自行拼装原生输入框。 |
| 所属分组 | `IxSelect` | 从已有分组中选择一个所属分组，同时允许快速新增分组 | 常规选择使用 `IxSelect`；需要允许新增分组名时使用 `allowInput` 并补充输入校验。 |
| 标签 | `IxSelect` / `IxTag` / `IxTagGroup` | 需要选择已有标签，也允许直接创建新标签 | 编辑态选择标签使用 `IxSelect`，需要创建新标签时使用 `allowInput`；只读标签回显使用 `IxTag` / `IxTagGroup`。 |
| 阈值 | `IxInputNumber` | 输入带固定单位的数值，例如 X 天、X Mbps、X 次 | 单位固定时通过 `addonBefore` 或 `addonAfter` 展示单位；需限制数值范围、步进和精度，并给出错误修正提示。 |
| IP 地址池 / NAT 地址映射 | `IxProFormList` / `IxProTable` | 某个字段需要配置并展示一组结构化数据，每次新增都在表格中增加一行 | 表单内动态多行配置优先使用 `IxProFormList`；需要表格化展示、行内编辑和行级校验时结合 `IxProTable`。 |

未命中上表的高频字段时，其组件选型依据 6. 组件选择原则 按组件类型判断。

## 4. 表单承载方式

表单承载方式应优先从 `../02-template/01-page-types.md` 已定义的页面模板中选择，不在本文重新定义页面容器。本文只补充表单复杂度对承载方式的影响。

默认对应关系（页面类型 ID 与 `../02-template/01-page-types.md` 定义一致）：

- 配置表单页（页面类型 ID：`page-form-config`）：使用页面级 `IxProForm`，适合独立菜单级配置、字段较多、需要稳定 URL 或长时间编辑的表单。
- 表单弹窗（页面类型 ID：`form-modal`）：使用 `IxProFormModal`，是从列表或详情发起的新建、编辑、复制类表单的默认承载方式。
- 表单抽屉（页面类型 ID：`form-drawer`）：使用 `IxProFormDrawer`，默认不使用；仅在用户额外说明或业务设计（product design）特别说明时才选用。
- 下钻步骤条配置页（页面类型 ID：`page-form-stepper`）：使用页面级 `IxProForm`，步骤流程按页面模板组织。

新增和编辑类表单默认使用表单弹窗（`form-modal`）承载；只有当字段数量、依赖关系、风险等级或编辑时长明显超出当前承载方式时，才建议切换页面模板，并说明原因。字段数量只作为辅助判断，不作为硬规则；若业务设计 Skill 或页面模板已明确承载方式，优先沿用已确定模板。

## 5. 分层与布局结构

### 5.1 是否拆分步骤

采用分步表单前，应先确认所有配置项是否属于同一个连续任务流程。只有当用户需要按阶段完成同一任务时，才适合分步。

默认判断基准：

- 表单项较多，单页展示明显超过常规桌面端一屏时，可考虑分步。
- 存在强前置依赖时，可考虑分步：首步选择会决定后续大部分配置内容，且后续差异显著。
- 步骤之间具有清晰阶段目标，例如“选择对象 → 配置策略 → 确认生效”。

不建议分步的情况：

- 配置项只是平行分类，并非连续流程。
- 用户需要频繁对照多个分组内容。
- 步骤拆分后会增加来回切换成本。

分步表单应补充：每一步的目标、是否允许返回修改、跨步骤校验方式、是否需要草稿保存、最后是否需要确认摘要。

### 5.2 是否启用左侧定位导航

当表单存在多个平行一级分类，且每个分类内容较长时，可采用“左侧定位导航 + 右侧表单内容”布局。默认判断基准是：一级分类较多、单分类内容明显超过一屏、用户需要在分类间快速跳转。

不满足以上条件时，优先使用普通单页分组，避免为少量内容引入过重导航。

### 5.3 高级设置

非核心、低频、辅助性的配置项可收敛至“高级设置”。高级设置默认收起，用于降低首屏复杂度。

收敛判定（主动收进高级配置的触发条件）：

当表单配置项总数超过 10 个时，逐项分析配置项属性，将同时满足以下三个条件的配置项收进高级设置，使首屏表单配置项不超过 8 个：

1. 非必填，或存在默认行为 / 默认值（用户不主动修改也能正常生效）；
2. 不属于核心业务的基础配置（偏向高阶使用功能）；
3. 不配置也能完成主要任务。

三个条件同时满足才收敛，任一条件不满足时该配置项保留在首屏；收敛后高级设置内配置项仍按正常表单项规则设计，仅默认收起，不因收敛改变必填、校验或默认值行为。

需要注意：

- 低频不等于低风险。高风险配置不得仅因低频而隐藏。
- 高级设置中存在非默认值、异常值或影响生效范围的值时，应在标题或摘要处提示状态。
- 高级设置的“展开 / 收起 UI 状态”可以不记忆；但高级设置内用户已填写的配置值必须保留。
- 当用户角色长期高频使用高级项时，可评估是否需要记忆展开状态或提升入口层级。

### 5.4 标题层级与分区

表单标题层级最多使用两级，避免出现 3 级及以上表单层级。

- 一级标题：表示主要配置分区。
- 二级标题：表示一级分区内的子主题。
- 同一层级的标题应使用一致样式。
- 同一个语义标题只呈现一次，避免同时作为分组标题和卡片标题重复出现。
- 不要为了制造“卡片感”额外增加分隔线、描边或装饰性标题栏；分隔线应服务于容器分区关系，而不是替代语义层级。

输出方案前应先给出标题层级映射，列出标题名称、层级、父级和采用样式，再进入具体字段和组件设计。

### 5.5 配置项聚合

需求中列出的待配置字段是数据清单，不等于界面上的配置项；拆成多少个配置项由设计决定。多个紧密相关的字段应聚合为一个配置项，由一组联动组件承载同一个 label，以减少配置项数量，并把字段之间的联动校验收敛到组件内部。

聚合判定（全部满足才聚合）：

- 同一业务语义：字段共同描述同一件事，单独配置任何一个都语义不完整（如地理位置的各级行政区、执行周期的频率与时间）。
- 取值同源或联动：后级字段的取值范围由前级字段决定（国家决定省市区选项；选每周后才出现周几）。
- 有成熟复合组件承载：聚合后有对应组件（级联选择器、联动选择组等，按 6.1 与 [下拉选择面板形态与增强](../03-widget-patterns/select-panel.md) 判定），无需手工拼装交互。

不聚合的情况：

- 字段之间无取值依赖也无共同语义（如名称与超时时间）。
- 聚合后没有对应复合组件承载，强行组合反而增加理解成本。

示例：

- 地理位置：国家、省、市、区与详细地址聚合为 1 个配置项"地理位置"，共 2 个组件——级联选择器承载国家/省/市/区（选项同源联动），输入框承载详细地址（无选项结构、无唯一性，独立组件）。若拆为 5 个独立配置项，"省的选项随国家变化"等联动会变成配置项之间的校验规则，数量与复杂度同步增加。
- 执行周期：大频率（每日/每周/每月）、小频率（周几/几号）与时间点聚合为 1 个配置项"执行周期"，共 3 个组件——频率选择框、随频率联动的取值选择框（选每周出周几、选每月出几号）、时间选择器。若拆为 3 个独立配置项，"选了每周才显示周几"的显隐联动会变成跨配置项校验。

输出要求：每个聚合后的配置项需标注由哪些需求字段聚合而来、label 名称与组件组合，确保需求字段无遗漏。字段的收敛承载方式不是复合组件而是自然语言句式时（数值驱动、效果抽象），按 5.7 判定。

### 5.6 配置项分组

先执行 5.3 收敛判定与 5.5 配置项聚合，再评估分组：高级设置内的配置项不参与首屏分组，避免对已收敛项重复分组。

分组依据：

- 默认按配置项属性分组：同属一个业务属性（如基础信息、生效方式、通知方式）或同一配置阶段的配置项归为一组。
- 分组标题必须能概括组内全部配置项，禁止使用“其他”“杂项”等兜底标题。

分组门槛：

- 每个分组下配置项不少于 2 个，分组总数默认不超过 4 个。
- 单个分组仅剩 1 项时，应并入语义最近的相邻分组；确实无法并入时才允许独立成组。
- 配置项规模很大（如业务确实需要 20 个配置项）时，分组数上限与首屏数量可按实际业务放宽，但仍按上述属性分组逻辑组织，禁止通过拆碎分组数量来制造“每组很少项”的形态。
- 不满足分组门槛时直接平铺，或用一级标题做分区，不引入分组容器。

禁止项：

- 多个分组且每组只有 1 个配置项的结构。
- 为视觉对齐或“卡片感”制造分组。

输出分组方案时，需说明每个分组的分组依据与组内配置项数，便于对照门槛评审。

### 5.7 配置项自然语言表达

当配置效果抽象、难以从字段名加裸数值直接理解时，可把配置组织成一句自然语言：句中仅数值为可编辑输入项，其余为固定文案。形态分两种：多字段聚合为一句（如 SLA阈值、带宽保护设置），单字段嵌入效果解释句（如中断阈值）。

与 5.5 的关系：多字段形态与 5.5 同属收敛为 1 个配置项，但承载方式不同——5.5 用成熟复合组件承载取值同源联动，本节用固定文案加句内数值槽位承载语义关系。先按 5.5 判定，命中复合组件条件时优先 5.5，未命中再按本节判定。

判定特征（同时满足才适合使用；需求原文形如"当X超过N时""最多允许N""连续N次则"等句式时优先考虑）：

1. 数值驱动：核心可变量是 1 个或少量数值（阈值、百分比、数量、时长、带宽），句子结构不随取值变化；
2. 效果抽象：配置生效后会发生什么无法从字段名直接看出，例如判定探测失败、限制备份并发、保障带宽；
3. 字段间有语义连接：字段通过"且/或/连续/最多/则"等关系构成完整业务语句，拆成独立表单项后该关系丢失，需额外说明弥补；
4. 可用业务语言稳定表述：句式不依赖技术黑话，固定文案不随用户取值改变含义。

不适用（任一命中则退回普通表单项加说明文案）：

- 纯选择类配置，选项本身语义已明确，如启用/禁用、执行方式；
- 字段间无语义关系，仅因同属一个分区而并列，如名称、备注、超时时间；
- 选择不同选项会切换整句结构，或句式分支多到固定文案无法覆盖；
- 句子超过一句或明显过长，自然语言反而增加阅读负担。

典型示例（[ ] 内为可编辑数值槽位）：

- SLA阈值：时延>[1000]ms，丢包>[5]%，抖动>[1000]ms —— 3 个阈值收敛为 1 个配置项，指标名、比较符与单位为固定文案。
- 中断阈值：连续[5]次探测无响应，则判断探测失败 —— 数值嵌在效果解释句中，固定文案承担效果说明职能。
- 带宽保护设置：允许最多[10]台设备同时进行设备备份任务，且每台设备请求最多占用[10]mbps带宽 —— 2 个数值与"最多/且"连接词组成一句，解释保护效果。

呈现规则：

- label 使用业务概念名，句子不紧跟 label 展示，放在控件列并与上下配置项的控件左对齐；句子按"固定文案 + 数值输入 + 单位"拼装；
- 句子换行规则：固定文案优先铺满当前行再自然换行；只有当换行位置刚好落在数值输入组件上、且剩余行宽不足以容纳组件的最小宽度时，才将整个组件换到下一行行首；不得为避让组件提前把整句换行，也不得压缩固定文案宽度强行塞入组件；
- 句内数值使用数字输入组件，按取值范围限制步进与精度，宽度按最大取值估算，不设独立 label；比较符是固定文案，不得做成可编辑项；单位通过输入框后置固定文案（`addonAfter`）展示在输入框内，需求未定义单位切换时单位固定不可编辑，需求明确支持单位切换时（例如"小时/天/周/月"或"时/分/秒"）按需求提供单位切换能力；
- 收敛后按 1 个配置项参与 5.3 收敛判定与 5.6 分组计数；
- 句内连接词必须与真实业务规则一致，不得为排版效果改动"且/或/连续/最多"等关系；
- 效果解释由句内固定文案承担时，不重复叠加同义的小 i 说明（见 8.1）；风险提示仍按 8.1 常驻展示。

输出要求：说明句式模板、槽位字段来源与固定文案清单，确保句内数值与需求字段一一对应、无遗漏。

## 6. 组件选择原则

本节承接 3. 常见字段组件映射速查，用于未覆盖字段的组件选型判断。

组件选择先满足任务效率和可理解性，再匹配产品实现层的组件库。

### 6.1 单选

默认判断基准：

- 选项少、文案短、需要直接比较时，使用平铺 Radio。
- 选项较多、占用空间大或无需频繁比较时，使用 Select。
- 选项数量较少，但选项在视觉上需要突出，或属于当前配置中的关键配置，且选择不同选项会切换不同配置项时，可使用单选卡片。
- 选项本身需要展示短解释、差异需要被快速比较时，可使用单选卡片。
- 卡片中除展示选项名称外，可增加辅助文字，说明该选项的效果、适用场景、风险或后续配置变化。
- 解释很长时，不要把大段说明塞入选项区域，应放到字段说明、帮助链接或模块说明中。

默认使用原始 Radio，保持表单控件轻量、易识别。只有在选项展示效率、阅读负担或视觉强调有明确诉求时，才调整为 Select 或卡片式单选组件。当选项数量较少且每个选项文案较短时，优先将选项平铺展示，方便用户直接比较和选择。当选项数量较多，或选项文字较长导致一行展示不完、出现换行或阅读负担时，可改为 Select，避免表单区域被选项撑开。

采用卡片时，卡片内容应完整展示，自然换行；同组选项卡片应在最终渲染效果中保持等高，不应通过省略、截断或隐藏溢出解决高度问题。

当单选选项会包含子配置项，且不同选项出现的配置内容存在明显子层级关系时，应将子配置项放在对应选项下方的子配置面板中。子配置面板应通过小三角箭头或同等从属关系提示指向对应的 Radio，让用户明确这些子配置从属于哪个选项。例如选中“定时升级任务”后需要配置执行时间，应将时间配置放入对应选项下方的子配置面板中。

示例：配置升级任务时，用户需要在“定时升级任务”和“立即升级”之间选择，这两个选项会影响后续配置项和执行方式，可使用单选卡片展示。卡片内可补充说明“按指定时间自动执行升级”或“提交后立即开始升级”，帮助用户理解选择结果。如果选择“定时升级任务”后需要填写升级时间，应在该选项下方展示带小三角箭头的子配置面板，面板内承载时间选择器、执行周期等配置项。

当单选载体确定为 Select 时，下拉面板内部采用哪种形态（平铺、平铺+搜索、分组+搜索、树+搜索、级联）以及是否叠加增强项（面板内新增、面板确定取消、选项辅助说明、选项禁用原因），统一按 [下拉选择面板形态与增强](../03-widget-patterns/select-panel.md) 判定：先按形态判定链确定唯一形态，再逐项判断增强项，不在本节重复约定。

### 6.2 多选

默认判断基准：

- 选项少、可直接浏览时，使用 CheckBox。
- 选项较多、需要搜索或节省空间时，使用多选 Select。
- 选项数量较少，但选项在视觉上需要突出，或属于当前配置中的关键配置，且选择不同选项会切换不同配置项时，可使用多选卡片。
- 多个选项都需要短解释，且用户需要比较差异时，可使用多选卡片。
- 卡片中除展示选项名称外，可增加辅助文字，说明该选项的效果、适用场景、风险或后续配置变化。

默认使用原始 CheckBox，保持表单控件轻量、易识别。只有在选项展示效率、阅读负担或视觉强调有明确诉求时，才调整为多选 Select 或卡片式多选组件。当选项数量较少且每个选项文案较短时，优先将选项平铺展示，方便用户直接比较和选择。当选项数量较多，或选项文字较长导致一行展示不完、出现换行或阅读负担时，可改为多选 Select，避免表单区域被选项撑开。

采用卡片时，卡片内容应完整展示，自然换行；同组选项卡片应在最终渲染效果中保持等高，不应通过省略、截断或隐藏溢出解决高度问题。

当多选选项会包含子配置项，且不同选项出现的配置内容存在明显子层级关系时，应将子配置项放在对应选项下方的子配置面板中。子配置面板应通过小三角箭头或同等从属关系提示指向对应的 CheckBox，让用户明确这些子配置从属于哪个选项。例如勾选“排除地址”后出现地址输入框，应将地址输入框放入对应选项下方的子配置面板中。

当多选载体确定为多选 Select 时，面板形态与增强项按 [下拉选择面板形态与增强](../03-widget-patterns/select-panel.md) 判定；需要“选完再生效”或选择会触发较重联动时，叠加面板确定取消增强，其余增强项按同一文档的兼容矩阵判断。

### 6.3 功能启用与状态控制

功能启用类控件在 Radio、Switch、CheckBox 之间选择。三者视觉重量与表达能力不同：Radio 表达互斥状态，Switch 视觉最重、适合强调功能，CheckBox 轻量、适合承载说明或展开子配置。

**规则、策略或状态的启用 / 禁用，优先使用 Radio。**

适用于状态本身是一个配置项的场景：切换只是在启用、禁用之间选择，不会影响其他配置项的显隐或可用状态。典型如规则、策略、审计开关等的状态配置。

```text
状态    (•) 启用   ( ) 禁用
```

**Switch 用于强调型的功能开关，分两种场景：**

场景一：单一功能的开启和关闭。功能本身就是一个独立开关，开启即生效，没有下属配置项。开关视觉上比 CheckBox 更重，适合需要强调的功能。

```text
客户端权限        [开关]
```

场景二：卡片级配置组的总开关。卡片承载一组配置，开关放在卡片标题右侧，控制卡片内全部配置项能否配置，形成对组内配置的局部全局控制。关闭后卡片内配置项置灰、不可编辑，已填写内容保留不丢失。

```text
┌─ 消息通知 ──────────────── [开关] ─┐
│  （关闭后以下配置置灰不可编辑）      │
│  通知方式    (•) 邮件  ( ) 短信     │
│  接收人      [请选择接收人]         │
└────────────────────────────────────┘
```

选型约束：Switch 视觉重量大，用于需要强调的功能开关；普通表单配置项的启停尽量少用 Switch，避免页面出现大量开关导致重点失焦。

**CheckBox 用于轻量的功能勾选，分两种场景：**

场景一：勾选项需要辅助文字说明功能效果。勾选项文案本身承载"这个功能具体做什么"的说明，勾选即表示接受该效果。

```text
密码安全  ( ) 首次登录强制修改密码
```

场景二：勾选后展开具体配置项。勾选表示启用该功能，同时在其下方展开子配置面板，承载该功能的具体配置内容。子面板样式遵循 6.1、6.2 的子配置面板规则，勾选与展开即时联动。

```text
绑定关系  ( ) 用户绑定IP/MAC
    └─ 子配置面板：绑定IP [______]  绑定MAC [______]
```

切换前置控制项时，应保留各选项下用户已填写的子配置值；再次切回时自动回填，避免误清空。

### 6.4 输入类

- 单行单值文本：使用 Input，可搭配前置或后置单位、协议、后缀说明。
- 纯数字值：使用 InputNumber，单位固定时直接展示单位，单位可切换时提供单位选择。
- 长文本：使用 Textarea。无特殊要求时应设置合理字数上限。
- 批量输入同类型多条数据：使用带行号或按行校验能力的多行输入组件，支持逐行提示错误。

## 7. 默认值、恢复默认与风险控制

能明确降低用户决策成本且风险可控的字段，应提供推荐默认值。高风险、强业务差异或需要责任确认的字段，不应默认代选，应让用户明确选择。

默认值设计应说明：

- 默认值是什么。
- 为什么适合作为默认值。
- 是否影响安全、权限、生效范围或成本。
- 用户修改后是否需要记忆。

当模块有一组通用推荐默认配置时，可提供“恢复默认设置”。恢复默认属于可能破坏用户配置的操作，必须二次确认，并明确说明会恢复哪些内容、是否影响已保存数据、是否可撤销。

高风险操作必须使用确认机制，例如关闭核心管控能力、删除配置、清空批量内容、恢复默认、改变大范围生效对象等。确认文案必须说明操作后果，避免只写“确定执行该操作吗”。

## 8. 说明文案设计

说明文案先判断解释对象，再决定呈现位置。

### 8.1 说明类型与位置

- 字段概念解释：解释单个字段的定义、作用或填写方式，小 i 图标放在 label 之后。
- 配置项与选项含义解释：解释控件的填写要求（如格式要求）、某个选项的含义、适用对象或影响，小 i 图标放在控件右侧，不放在 label 后。
- 模块原理整体解释：解释分组模块的原理、规则或复杂背景，使用可点击的链接（如"了解执行策略的判定规则"）放在分组小标题右侧，点击跳转独立说明页，不使用小 i 提示入口。
- 风险提示：说明当前选择会造成的重要后果，以常驻文字直接展示在对应选项或控件下方，不收进小 i 提示入口。

四类说明在表单中的位置关系：

```text
┌─ 分组小标题：执行策略（了解判定规则） ───────────────────┐
│                                                        │
│  执行方式 ⓘ             [ ● 立即执行 ]  [ ○ 定时执行 ]  │
│                                                        │
│  端口范围               [ 6379      ] ⓘ                 │
│                         ⚠ 关闭后策略立即失效且不可恢复， │
│                           请谨慎操作。                   │
│                                                        │
└────────────────────────────────────────────────────────┘
```

- 分组小标题右侧的可点击链接：承载模块整体原理解释（整体规则、背景），点击跳转独立说明页，不使用小 i。
- label 后的小 i：承载字段概念解释（这个字段是什么、为什么要填）。
- 控件右侧的小 i：承载配置项与选项含义解释（格式要求、选项含义与影响）。
- 控件或选项下方的常驻文字：只用于风险提示，带警示标识，不使用小 i。

用户把文案称为“说明”时，不应直接外放；仍需根据它解释的是字段、单个选项、整个模块还是风险后果进行分类。

配置项按 5.7 采用自然语言句式表达时，效果解释由句内固定文案承担，不叠加同义的小 i 说明；风险提示仍按本节规则常驻展示。

### 8.2 内容质量标准

说明文案应满足以下要求：

- 说明“作用 / 影响 / 适用场景 / 风险”中的必要内容，不写无信息量文字。
- 避免重复 label，例如 label 已是“任务名称”，说明不应写“请输入任务名称”。
- 避免技术黑话，优先使用用户可理解的业务语言。
- 风险提示必须明确后果，例如影响范围、是否中断服务、是否不可恢复。
- 错误提示必须说明如何修正，而不只是说明“格式错误”。
- 解释类文案默认收起，只有会影响当前决策且必须即时看到的风险或后果提示才常驻展示。

## 9. 校验与错误反馈

表单校验应覆盖必填、格式、范围、重复、跨字段依赖和异步结果。

- 必填项应明确标记。提交时未填写，应在字段附近提示，并帮助用户定位。
- 格式校验应说明正确格式，例如 IP、域名、手机号、邮箱、时间范围等。
- 跨字段校验应说明冲突字段和修正方式。
- 批量输入应支持定位到具体错误行或错误项。
- 异步校验应有加载反馈、失败反馈和重试方式。
- 分步表单提交失败时，应能定位到具体步骤和字段。
- 保存失败时，应保留用户已输入内容，不得让用户重新填写。

错误提示应使用可操作语言，例如“请输入 1-65535 之间的端口号”，避免只写“输入不合法”。

## 10. 状态与响应式

表单方案应覆盖正常编辑态之外的状态：

- 加载态：字段、默认值或选项加载中时的反馈。
- 空状态：没有可选对象、没有匹配结果或列表为空时的说明与下一步入口。
- 禁用态：因权限、依赖条件或策略锁定导致不可编辑时，应说明原因。
- 只读态：查看或无权限场景下，字段应转为可读展示，而不是保留不可用控件堆叠。
- 异常态：选项加载失败、保存失败、校验服务失败时，应提供重试或恢复路径。
- 保存中：提交后应防止重复点击，并展示处理反馈。

响应式设计应至少检查：

- 窄屏下 label 与输入区是否需要上下排列。
- 弹窗、抽屉和页面内容区宽度是否足够承载主要字段。
- 左侧定位导航在窄屏下是否需要折叠或改为顶部定位。
- 卡片组选项是否完整换行、等高且操作入口不溢出。
- 长 label、长选项、国际化文案是否会破坏布局。

## 11. 前端表单状态契约

涉及代码实现或设计交付给前端时，应输出 `form_state_contract`，确保视觉结构变化不会破坏表单状态链路。

每个一级分组至少说明：

- `group`：分组名称。
- `value_path`：字段值路径。
- `registration`：字段注册方式。
- `validation`：校验规则。
- `dirty_source`：脏数据来源。
- `change_tracking`：变更记录方式。
- `serialization`：提交序列化方式。

同一字段的初始化、读取、校验、dirty、变更确认和提交必须使用一致的数据路径。字段 `id` 不应替代组件 API 中负责表单注册的 `name`。

纯视觉调整默认保持 `form_state_contract` 不变；确需改变时，应把保存、取消、返回、复制和路由离开加入 `regression_scope`。

## 12. 输出结构建议

表单设计方案建议按以下结构输出：

1. 输入摘要与默认假设。
2. 前置确认项。
3. 表单承载方式与理由。
4. 标题层级映射。
5. 表单结构与字段分组。
6. 字段组件映射。
7. 默认值、校验和说明文案。
8. 风险操作与二次确认。
9. 状态与响应式要求。
10. `form_state_contract`。
11. `visual_contracts`。
12. `regression_scope`。
13. 后置确认项。
14. 自检结果。

## 13. 自检清单

输出前逐项检查：

- 是否区分通用方法层与产品实现层，没有把具体组件库或内部样例误写成通用原则。
- 表单承载方式是否综合任务复杂度、风险、上下文和字段数量判断，未把数字阈值当作绝对规则。
- 配置项超过 10 个时是否执行了收敛判定，同时满足非必填或有默认值、非核心基础配置、不配置也能完成主要任务三个条件的配置项是否已收进高级设置，首屏配置项是否不超过 8 个。
- 分步、单页、左侧定位和高级设置是否符合触发条件。
- 高级设置的展开状态和用户填写值是否分别处理。
- 组件选型是否符合选项数量、解释需求、比较需求和实现约束。
- 标题层级是否最多两级，且同一语义标题没有重复呈现。
- 配置项是否按属性分组，每个分组不少于 2 个（仅 1 项时已并入语义最近的相邻分组或说明无法并入的原因），分组总数默认不超过 4 个（超出时是否基于业务实际规模）。
- 默认值是否只用于降低决策成本且风险可控的字段，高风险字段没有默认代选。
